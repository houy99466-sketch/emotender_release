## 0. 今晚会议需要得到的结论

这次会议不需要讨论所有长期设想，而需要确定以下七件事：

1. **产品主链路**：是否正式确定为“表达此刻状态 → 连续对话 → 个性化饮品方案 → 用户调整 → 附近喜茶门店”。
2. **首个饮品数据范围**：只适配喜茶；首版只覆盖一个演示城市、附近 3 km 和少量经过核验的饮品及可调整项。
3. **情绪判断标准**：采用“维度评分 + 类别标签 + 本轮证据 + 置信度”，不继续只让 LLM 自由判断情绪名称。
4. **MiMo 接入边界**：MiMo ASR、MiMo 对话模型和 MiMo TTS 分别是否进入首版；额度与模型权限由谁确认。
5. **移动端技术范围**：近期继续使用现有 Web UI 封装 APK，还是进行 Kotlin/Compose 重写。基于当前周期，建议先保留 Web UI 封装 APK。
6. **门店功能边界**：首版只展示最近三家喜茶门店、距离和位置，不做下单、支付、取饮码或真实履约。
7. **冻结时间**：确定停止增加功能、开始完整回归和路演准备的日期。

## 1. 产品定位

### 1.1 小米比赛版的一句话

EmoTend 此刻一杯是一款基于 Xiaomi MiMo 的个性化饮品共创应用：用户通过语音或文字讲述当下经历与口味需求，系统理解本轮状态，结合长期口味偏好和真实门店菜单，生成一份可继续调整、可以在附近门店实际选择的饮品方案。

### 1.2 聚焦场景

首版只解决一个场景：

> 用户下课、下班或短暂休息时，不想研究复杂菜单，只想说出今天发生了什么，并得到一杯符合此刻状态和个人口味的饮品建议。

它不是心理咨询工具，也不是一个泛化智能家居入口。饮品是理解用户之后产生的具体结果。

### 1.3 首版产品边界

首版做：

- 语音与文字输入。
- 连续多轮对话。
- 本轮情绪与需求分析。
- 长期口味偏好和饮食限制。
- 基于真实喜茶菜单范围生成方案。
- 用户调整甜度、温度、口感等允许选项。
- 展示附近 3 km 内最近的喜茶门店。
- 生成并保存本次饮品报告。

首版不做：

- 机器人、机械臂、实体调制和递杯。
- 真实下单、支付、库存和取饮码。
- 多品牌同时适配。
- 米家灯光或其他智能家居联动。
- 心理疾病判断、心理治疗或医学建议。
- 为了形式而进行的大规模移动端重写。

- 情绪占比饼图和来源说明。

- 当前没有使用 Xiaomi MiMo。
- 当前 LLM 仍由 OpenAI 兼容中转接口提供。

- 没有喜茶菜单和 DIY 可选项数据库。
- 没有原料、过敏源、咖啡因、乳制品等确定性约束引擎。

- 普通 Windows 浏览器录音接口仍沿用 Linux/macOS 录音逻辑；当前只建议测试文字输入。
- 当前 APK 是 Web UI 封装，不是完整 Kotlin/Compose 原生界面。

## 6. 情绪判定如何降低主观性

### 6.1 公开研究中可以借鉴的框架

不存在一个适用于所有对话的唯一“客观情绪真值”。但可以用成熟框架约束 LLM：

1. **Russell 情感环形模型**：使用愉悦度（Valence）和唤醒度（Arousal）描述情绪位置，比直接让模型自由造标签更稳定。
2. **PAD/VAD**：在 Valence、Arousal 基础上加入 Dominance，即控制感或主导感，可区分“紧张但有行动力”和“紧张且无力”。
3. **Geneva Emotion Wheel**：提供经过理论与实证研究的情绪类别和强度表达方式，适合参考类别组织方式。
4. **NRC 情绪词典**：提供八种基本情绪及正负向关联，也提供 VAD 和强度相关词典，可作为词汇辅助，但其许可和中英文适用性必须单独确认。
5. **SAM 自评方法**：让用户自己反馈愉悦度、唤醒度和控制感。产品不必每轮展示量表，但可以提供“分析不准确”或轻量修正入口。

### 6.2 推荐的产品实现

情绪模块不直接输出一句“用户很焦虑”，而输出：

```json
{
  "emotion_assessment": {
    "valence": -0.45,
    "arousal": 0.72,
    "dominance": 0.30,
    "primary_label": "焦虑",
    "secondary_labels": ["疲惫"],
    "confidence": 0.78,
    "evidence": [
      {
        "quote": "明天就要答辩了，我脑子停不下来",
        "interpretation": "负向体验、高唤醒、控制感偏低"
      }
    ],
    "clarification_needed": false
  }
}
```

建议范围：

- `valence`：`-1.0` 到 `1.0`。
- `arousal`：`0.0` 到 `1.0`。
- `dominance`：`0.0` 到 `1.0`。
- `confidence`：`0.0` 到 `1.0`。

### 6.3 Prompt 约束

情绪 Prompt 至少包含以下规则：

1. 只使用本轮对话证据判断当前状态。
2. 长期 profile 只参与口味和沟通偏好，不参与本轮情绪分数。
3. 必须引用用户原话或同轮事实，不能凭空补充原因。
4. 先计算 VAD，再选择类别标签，不能先选标签再倒推理由。
5. 用户明确自述优先于模型从措辞进行的推断。
6. 同时存在多种状态时保留主次情绪，不强行压成单标签。
7. 证据不足时降低 `confidence`，并提出一个澄清问题。
8. 不输出心理疾病、人格或医学诊断。

### 6.4 需要建立的测试集

至少准备 30 至 50 条测试语句，覆盖：

- 正向高唤醒：兴奋、庆祝。
- 正向低唤醒：平静、满足。
- 负向高唤醒：焦虑、烦躁、紧张。
- 负向低唤醒：疲惫、低落、失望。
- 混合情绪：开心但紧张、疲惫但想行动。
- 否定表达：我不是难过，只是累。
- 反讽和口语表达。
- 证据不足和无关输入。
- 历史状态与本轮状态冲突。

验收重点不是“模型是否猜中一个词”，而是：VAD 方向是否合理、引用证据是否真实、置信度是否匹配、是否正确触发澄清。

## 7. 喜茶饮品库与 DIY 数据

### 7.1 首版数据策略

本次公开网页调研没有确认喜茶提供面向第三方的公开菜单、DIY 或下单 API。因此首版不能假设存在可直接调用的官方接口。

建议采用：

```text
喜茶 App/小程序公开可见内容人工采样
→ 记录演示门店、商品和可选项
→ 人工复核
→ 转换为本地结构化 Catalog
→ Demo 只在已核验范围内推荐
```

不要绕过登录、签名或访问控制抓取私有接口。若后续获得官方合作或接口说明，再替换数据 Provider。

### 7.2 需要采集的字段

| 数据对象 | 必需字段 |
|---|---|
| 品牌 | 品牌名称、来源、核验日期 |
| 门店 | 门店名称、地址、经纬度、采样日期 |
| 商品 | 商品名称、分类、基础描述、默认配置、图片来源 |
| 规格 | 杯型、温度、冰量、甜度 |
| 基底 | 茶底、奶基、果味或咖啡基底 |
| 小料 | 可添加、可移除、互斥、数量限制 |
| 限制 | 不可修改项、仅部分门店提供、时间限制 |
| 饮食信息 | 乳制品、咖啡因、常见过敏源；没有可靠信息时标记未知 |
| 来源证据 | 截图编号、采样门店、采样日期 |

所有具体字段名称和允许值必须从实际页面采样，不在代码中凭感觉补齐。

### 7.3 饮品库不是话术库

LLM 负责理解用户和生成自然解释；Catalog 和约束程序负责保证结果真实：

```text
LLM 输出需求向量
→ 程序筛选真实商品
→ 程序应用合法 DIY 选项
→ 程序重新计算六维风味
→ LLM 基于已验证结果生成推荐理由
```

LLM 不应直接创造商品名称、门店不存在的原料或不受支持的调整组合。

### 7.4 六维图的后端化

当前六维图为前端演示值：

`甜度、茶感、奶香、果香、清爽度、口感层次`

下一步需要把每个基础商品和可选项转换成确定性增量。例如：

- 低甜：降低甜度。
- 增加茶底浓度：提高茶感，具体是否允许必须来自商品规则。
- 更换奶基：影响奶香和口感层次。
- 添加果味：影响果香和清爽度。
- 添加脆啵啵等小料：影响口感层次。

具体增量数值需要通过团队统一标注或测试确定，不能继续只在前端写死。

## 8. 附近门店功能

### 8.1 首版流程

```text
用户授权定位
→ 获取当前经纬度
→ 搜索 3 km 内关键词“喜茶”的 POI
→ 按直线距离或地图返回距离排序
→ 显示最近三家门店
→ 用户点击后打开地图或门店详情
```

### 8.2 实现选择

可以使用高德开放平台的地图/POI 能力，但必须先申请 Key，并核对移动端 SDK 或 Web 服务 API 的调用方式、额度、隐私政策和坐标系。

页面只需新增：

- 推荐确认页或最终报告底部的“查看附近门店”按钮。
- 最近三家门店列表。
- 门店名称、距离、地址和地图入口。
- 定位拒绝、没有结果和接口失败状态。

### 8.3 演示兜底

比赛现场必须准备一份带 `mock` 标识的演示门店数据。真实定位或地图 API 失败时可以切换到预设地点，但不能把模拟距离伪装成实时结果。

## 9. MiMo 适配

### 9.1 当前差距

现在三条模型链路都不是 MiMo：

| 能力 | 当前实现 | 目标实现 |
|---|---|---|
| ASR | Android 系统语音识别 | MiMo ASR |
| 对话与结构化分析 | OpenAI 兼容中转模型 | 比赛允许的 MiMo 对话模型 |
| TTS | 未形成稳定主链路 | MiMo TTS |

### 9.2 官方资料已经确认的能力

截至 2026-07-25，MiMo 官方文档列出：

- `mimo-v2.5-asr` 语音识别模型。
- `mimo-v2.5-tts` 语音合成模型。
- `mimo-v2.5-tts-voiceclone` 音色复刻。
- `mimo-v2.5-tts-voicedesign` 音色设计。

具体比赛账号可用模型、额度、速率限制和调用方式仍需拿到主办方权限后实测。对话模型名称必须以当时控制台和比赛说明为准，不能提前写死。

### 9.3 建议架构

不要在业务代码里到处替换模型名。新增 Provider 边界：

```text
SpeechToTextProvider
├─ MiMoASRProvider
└─ TextInputFallback

DialogueProvider
├─ MiMoDialogueProvider
└─ ExistingOpenAICompatibleProvider（仅开发回退）

SpeechProvider
├─ MiMoTTSProvider
└─ SilentFallback
```

后端业务只依赖统一接口。API Key、Base URL 和模型名全部放入 `.env`，不提交 GitHub。

### 9.4 接入顺序

1. 先接 MiMo 对话模型并保证结构化输出稳定。
2. 再接 MiMo ASR，保留文字输入兜底。
3. 最后接 MiMo TTS；如果时间不足，TTS 可以作为增强项，但路演必须明确已经使用了哪些 MiMo 能力。
4. 对每个 Provider 增加超时、重试、错误提示和开发回退。

## 10. UI 与美观性

当前浅色版已经完成视觉方向转换，近期不建议再次做大规模布局重写。应做的是统一和补齐：

### 10.1 保留

- 浅灰白背景、珊瑚橙主操作、湖蓝与薄荷绿辅助色。
- 动态表情和连续聊天。
- 推荐确认、规格调整和最终报告三段式结构。
- 六维图、情绪饼图和保存图片。

### 10.2 优先优化

- 将“情绪酒保”“老柯”“调酒”等文字统一改成比赛版饮品共创表达。
- 给聊天、推荐、报告建立一致的标题和按钮规范。
- 在规格调整中只显示当前商品真实支持的选项。
- 把附近门店做成一个明确按钮和独立列表，不把地图直接塞进主页面。
- 增加加载、空结果、定位拒绝、模型失败和离线演示状态。
- 保证小屏手机上标题、六维标签、门店地址和长文本不截断。
- 报告中的饮品名称、配方和六维值必须来自同一个最终对象。

### 10.3 暂时不要做

- 为每杯定制饮品生成或随机匹配实物图片。
- 大量装饰动画和与主流程无关的页面。
- 在赛前重新开发完整 Compose 设计系统。
- 同时支持多个茶饮品牌。

## 11. 还需要补上的关键工作

除情绪标准、饮品库、门店和 UI 外，还需要讨论以下工作：

1. **统一数据协议**：确定情绪、饮品方案、门店和 profile 的最终 JSON Schema。
2. **确定性校验**：模型输出必须经过菜单、DIY 选项和饮食限制校验。
3. **评测集**：建立情绪判定、模式切换、饮品推荐和 profile 污染测试。
4. **数据溯源**：每条商品和门店数据记录来源与核验日期。
5. **隐私边界**：定位、语音、对话和 profile 分别如何授权、保存和删除。
6. **演示降级**：MiMo、地图或网络失败时，文字输入和带标识 Mock 数据如何接管。
7. **延迟指标**：记录 ASR、对话模型、饮品校验和页面渲染分别耗时。
8. **发布流程**：固定 APK 版本号、构建方式、签名、安装测试和回退包。
9. **路演脚本**：准备一条 90 秒稳定主流程和两条备选输入。
10. **事实表述**：区分已实现、Mock、规划和需要品牌授权的能力。

## 12. 待分配任务包

以下任务先不指定负责人，会议中根据能力和依赖分配。

### T0：产品与技术范围冻结

**目标**：确定比赛版只做什么、不做什么。  
**交付物**：一页范围清单、最终用户链路、冻结日期。  
**验收**：团队对喜茶范围、门店边界、MiMo 范围和 APK 形态没有冲突理解。  
**依赖**：无，必须最先完成。

### T1：情绪标准与 Prompt

**目标**：将 VAD/PAD、类别、证据、置信度和澄清机制写入 Prompt。  
**交付物**：情绪规则文档、JSON Schema、30 至 50 条测试集、基准结果。  
**验收**：历史情绪不污染本轮；每个判断有本轮证据；低置信度会澄清；不进行医学诊断。  
**依赖**：T0。

### T2：喜茶菜单与 DIY 数据采样

**目标**：建立首批真实商品和允许调整项。  
**交付物**：采样表、截图证据、本地 Catalog JSON、核验日期。  
**验收**：每个选项都能追溯到实际页面；没有凭空添加的茶底、小料或规格。  
**依赖**：T0。

### T3：饮品约束与六维计算引擎

**目标**：让饮品配置、六维图和最终配方保持一致。  
**交付物**：配置对象、约束规则、六维计算函数、校验测试。  
**验收**：用户修改规格后，配置、六维图、推荐说明和最终报告同步变化；非法组合被拒绝。  
**依赖**：T2。

### T4：附近门店

**目标**：显示 3 km 内最近三家喜茶门店。  
**交付物**：定位权限、POI Provider、门店列表、地图入口、Mock 降级。  
**验收**：真定位、拒绝定位、零结果、接口失败和 Mock 五种状态都可以演示。  
**依赖**：T0；可以与 T1、T2 并行。

### T5：MiMo Provider 适配

**目标**：替换当前 ASR、对话模型和 TTS 链路。  
**交付物**：Provider 接口、MiMo 实现、环境变量说明、超时与错误处理。  
**验收**：路演主链路明确调用 MiMo；结构化输出通过校验；API Key 不进入仓库。  
**依赖**：主办方额度、官方模型权限、T1 的结构化输出。

### T6：UI 文案与门店入口

**目标**：把当前浅色页面改成完整的广义饮品产品表达。  
**交付物**：统一文案、真实规格选项、附近门店按钮与列表、异常状态。  
**验收**：页面不再出现不合时宜的酒保、调酒和酒精配方内容；移动端无溢出和遮挡。  
**依赖**：T2、T3、T4 的数据协议。

### T7：用户档案与隐私

**目标**：将长期档案改为口味和饮食限制导向。  
**交付物**：profile Schema、授权说明、查看/修改/删除设计、摘要 Prompt。  
**验收**：历史 profile 不改变本轮情绪；用户可以删除；定位和语音不默认长期保存。  
**依赖**：T0、T1。

### T8：自动测试、发布与路演

**目标**：形成可安装、可回退、可稳定演示的成品。  
**交付物**：自动测试、APK、安装指南、演示脚本、回退包、已实现清单。  
**验收**：至少两台 Android 设备完成完整链路；连续演示三次无阻断；网络失败时可以降级。  
**依赖**：所有 P0 任务。

5. 页面展示本轮证据、情绪维度和推荐理由。

11. 模型或地图失败时有明确提示和降级路径。
